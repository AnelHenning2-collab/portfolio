01
Origin & Requirements
Starting From a Real Requirements-Gathering Process

The Concept

TransitionTrack began as a DevOps and database-design coursework project at Rasmussen College, built around a case scenario: a busy marketing-company CEO, buried in scattered tasks and disruptive stop-and-go meetings during the 2020 shift to remote work, needed one custom application to hold research, status updates, requests, discussions, journaling, notecards, teaching notes, and reference material in a single place. I ran the project the way a real engagement runs — creative brief, wireframe, and a working prototype — under my own studio name, Logika Labs.

In My Own Words

"The brief was fictional, but the design discipline wasn't. Once I mapped what I was actually asking users to do — chunk, chew, and change what they're learning — I recognized it as the same tool I needed for my own transition, and kept building it after the assignment ended."

02
Information Architecture
The Real Menu Structure

The Concept

The full app maps to eight main sections, each built around a real behavior: tracking what you know versus don't know yet, pushing status updates out the door, requesting help, discussing with a mentor or manager, journaling to process a decision, drilling notecards to retain new material, teaching concepts back to check understanding, and researching an archive of prior work. Every section was scoped down to its own sub-menu before a single screen was drawn.

In My Own Words

"I designed this because I needed it. The menu isn't a generic task list — it's the actual shape of how I process a hard transition: research it, journal about it, teach it back to myself, then check the status."

03
Prototype & Build
From Wireframe to Working Code

The Concept

Before this became a Figma/Adobe XD design exercise, the earliest working version was a real Java console application — built and debugged in Eclipse — that walked a user through onboarding, menu selection, and each core interaction (discuss, teach, journal, summary, preferences) as command-line prompts. It ran, and it worked, before a single pixel was designed. Since then it's grown into a visual UI system and an in-progress desktop-app scaffold, built to eventually package as a real installable application.

In My Own Words

"Designing an app and actually building one are different disciplines. Getting the logic to run in Eclipse first — before I ever opened Figma — meant every screen I designed afterward was designing around something that already worked, not just something that looked right."
